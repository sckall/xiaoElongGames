> **给维护者**：商业化与 Steam 上架是大方向决策，**不要在没读这份文档前动手改协议或加付费字段**。

## 一、商业化前的诚实判断

### ✅ 当前架构「已经能用」的部分

| 设计 | 为什么适合商业化 |
|------|----------------|
| **无数据库、内存态房间** | 部署极简；`Dockerfile` + `docker-compose.yml` 已有 |
| **服务端权威**（回合制 getView 投影 + realtime tick 推 snapshot） | 防作弊的硬底子 |
| **平台/游戏契约**（`games/types.ts` + `registry.ts`） | 加新游戏 = 一个目录（成本小） |
| **静态前端 + 同端口托管** | CDN 友好；GitHub Pages 已验证可行 |
| **包结构清晰**（apps/games/packages/scripts/docs） | 多团队协作有边界 |
| **roomCode 4 位 + token 重连** | 上线初期够用，可平滑替换 |

### ⚠️ 商业化「必修课」（按紧急程度）

**1. 数据持久化（最大缺口）**
- 账号系统：游客 → 微信/邮箱/手机 OAuth（最少 1 种）
- 对局日志：每局写入数据库（合规、防纠纷、做 AI 训练数据）
- 计费/订单：支付回调、虚拟币、礼包
- 反作弊/风控日志

> **推荐栈**：PostgreSQL（主数据 + JSONB 存对局快照）+ Redis（房间态、会话、限流、ZSET 排行榜）+ 对象存储（OSS/S3 存截图/录像）

**2. 用户匹配 & 房间码升级**
- 4 位房间码（~100 万组合）做社交房够用
- 商业化需要 MMO 风格的 lobby + matchmaking（按分/Elo/延迟）
- token 重连要扩到「跨设备登录」

**3. 可观测性 & 限流加固**
- 当前 `/healthz` 只返回 uptime+roomCount；需要 Prometheus 指标（在线人数、tick 延迟、输入带宽）、结构化日志（Grafana/Loki）、慢调用告警
- 「每 IP 建房/连接上限」要扩到「每账号」+ 黑名单 + WAF
- `SECURITY.md` 清单要扩：`TRUST_PROXY` 一定要开（反代后部署），加 CSP/速率限制

**4. 合规 & 法务**
- 实名/防沉迷（中国大陆必做）
- 隐私协议、用户协议、未成年人保护
- 数据出境合规（如涉及海外）

### 🎮 商业化「加分项」（做了能拉高 ARPPU）

| 模块 | 实现路径 |
|------|----------|
| **英雄/皮肤/武器商城** | 出包魔法师：扩卡牌主题包；鳄龙咆哮：5 英雄外观 + 4 武器皮肤；用 `gameplay.json` 已有的可配置通道做 ID 化资源系统 |
| **赛季/通行证** | 单独 `services/season-svc`，前端 `BattlePassScreen.tsx` |
| **观战/直播/录像** | realtime snapshot 已落库，做回放；接 OBS / B 站直播不复杂 |
| **AI 教练/复盘** | 出包魔法师「AI 只用视角信息」天然适合做回放分析；鳄龙咆哮 tick 历史可做击杀热力图 |
| **电竞/排行榜** | Redis ZSET 一周排名，前端 `LeaderboardScreen.tsx` |

### 🚫 这套架构「不合适」的地方

1. **无持久化 = 不能做付费**（订单要对账）
2. **单机包 `pack-local.mjs`** 是给朋友体验的，**不能作为分发渠道**——商业化必须走服务端
3. **`games/corcodragon-fire/` 还在仓库里**（已归档），会让玩家搜到不该搜的 URL，建议打包时物理排除或完全移除
4. **GitHub Pages 部署文档** 面向开源/演示场景，**不能**用于商业（服务条款禁止商业用途）
5. **房间码 4 位 + 无 token 防扫**——商业化需要「邀请码/链接」「房间搜索」「创建者 ID 可见」
6. **没有 i18n**——出海要做

## 二、Steam 上架：架构适配分析

### 核心结论

**Web 优先的项目，搬 Steam 要做一次较大的形态切换；但项目里 80% 的代码能复用，工作量集中在「打包形态」+「Steam 集成」+「合规」三块。**

### 形态对比

| 维度 | Web 现状 | Steam 预期 |
|------|----------|-----------|
| 入口 | 浏览器 URL | Steam 客户端点击运行（桌面应用） |
| 分发 | 服务器静态托管（dist） | Steam 客户端下载安装包 |
| 启动 | 双击启动 / URL | 通过 Steam 启动器 / `steam://run/<appid>` |
| 联网 | Socket.IO 直连服务器 | **Steamworks P2P（VAC）或 Steam 服务器** |
| 成就/云存档/邀请 | 自建 token + localStorage | **必须接 Steamworks SDK** |
| 支付 | 无（HTML 静态） | Steam 强制走 Steam 钱包结算 |
| 上架审核 | 无 | Steamworks 上架审核（页面、年龄、地区） |

### 推荐的形态：Electron + Steamworks

**Web 整套当「内核」，套一层 Electron 外壳**。这是 Steam 上架桌游 / 休闲游戏的标准做法（Stumble Guys、Skribbl.io 网页衍生都是这条路）。

```
Steam 客户端点击运行 ↓
Steamworks 启动 → electron.exe + game.asar
   ↓
Electron 主进程：
 ├─ 加载 apps/web/dist 静态文件到 BrowserWindow（你 80% 的代码原样用）
   ├─ 注入 Steam 上下文（steamworks.js / greenworks）
   └─ 走 Steamworks P2P 或 Steam 鉴权（替代 Socket.IO 直连）做联机
   ↓
浏览器内核（Chromium）：React + Three.js + 你所有游戏 UI 原样跑
```

## 三、联机改造：两个方案

### 方案 A：保留 Socket.IO + Steam 鉴权（**推荐 MVP**）

- 服务器加一个 `/auth/steam` 端点
- 启动器用 Steam Ticket 兑换 session token
- 协议 `playerId` 改为 SteamID（string）
- **工时**：1 周
- **风险**：低
- **上限**：500-1000 同时在线（取决于服务器带宽）

### 方案 B：Steam P2P（更大改动）

- 主机当权威（选房主或最低延迟者）
- 其他客户端用 Steam Networking Sockets 直连
- 服务端只做「Steam 鉴权 + 房间列表匹配」
- **工时**：3-4 周
- **风险**：中（NAT 穿透、主机掉线迁移）
- **上限**：理论无限

### 推荐路径

```
方案 A 跑通 MVP
   ↓ （规模上来后）逐步迁移
方案 B（Steam P2P）
```

## 四、最大坑：中国大陆 Steam 上架 = 版号

⚠️ **中国大陆上架 Steam 的游戏必须取得「网络游戏出版物号（版号）」**——这是一个**国家级审批**，目前（2024-2025）版号发放周期 **6-18 个月**，且**独立游戏排队靠后**，成功率逐年下降。

### 现实路径

| 目标市场 | 是否需要版号 | 上架难度 |
|---------|------------|---------|
| 海外（Steam 全球）| 不需要 | 中（Steam 审核 + IARC 分级）|
| 中国大陆 Steam（蒸汽平台） | **必须版号** | 极高 |
| 香港/台湾/澳门 | 通常不需要 | 低-中 |

### 实际策略（国内独立游戏通用）

1. **先上 Steam 全球版**（不含中国大陆地区），主攻欧美/东南亚/港澳台
2. 积累玩家口碑、销量
3. **同时申请版号**（找代理公司，30-80 万 + 6-12 个月）
4. 拿到版号后 → 在 Steam 后台「中国大陆区」上架

### 项目优势

- 出包魔法师是回合制桌游，**不涉及暴力血腥**，IARC 分级应该是 E / E10+
- 鳄龙咆哮是 FPS，但属于卡通低多边形（KayKit / Kenney 风格），**没有写实血腥**
- 单人 vs AI 完全在浏览器内闭环 → **离线可玩**（Steam 现在很看重）

## 六、「现在就能做」的低成本准备（避免后期大改）

每个都是 1-3 小时工作量，但能避免后期大返工：

1. **`gameplay.json` 资源全部 ID 化**（卡牌、英雄、武器、皮肤各分配不会变的 `id`） → 商城/成就都用得到
2. **本地存储抽到 `apps/web/src/storage/`，命名空间化**（`tm-settings`、`tm-tokens`） → 云存档/迁移好做
3. **`protocol.ts` 加 `userId` 字段**（现在没有用户体系，加上预留） → 接入 Steam 不用双端改协议
4. **错误处理统一封装**（不要 console.error 直接抛） → Steam Crash 报告能拿到
5. **本地化抽取**（即使只做 zh-CN） → 上架时需要 zh-CN/en-US 双语商店页
6. **Steam 风格的 UI 改造**（占位、加载动画、版本号显示在角落） → 商店截图好看
7. **`playerId` 类型预留**：当前是 UUID（`packages/rules/protocol.ts`），未来用 SteamID（string）。**接口设计要兼容两种 ID**

> 这些任务的当前进度见 [ROADMAP.md](ROADMAP.md) § 阶段 0 任务表。

## 八、一句话总结

**架构骨架适合商业化**（平台/游戏分层 + 服务端权威 + 静态分发），但「**无持久化、无账号、无合规、无可观测**」是商业化前必须补齐的四个硬伤。其它商业化功能（商城/赛季/排行榜/观战）都有清晰的扩展点，工作量在「应用层」而非「架构重写」。
